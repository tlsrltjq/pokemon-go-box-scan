## 0. 한눈에 보는 핵심 결정

이 프로젝트는 단순 도감이나 육성 계산기가 아니라, **실제로 내가 보유한 포켓몬을 목록으로 확인하고 그 포켓몬만으로 레이드에 가장 높은 화력을 내는 6마리를 선정하는 개인용 도구**다.

### 0.1 확정 사항

| 주제 | 확정 결정 |
|---|---|
| 사용자 | 본인 1명만 사용. 공개 서비스 및 앱스토어 출시를 목표로 하지 않음 |
| 1차 목표 | Pokémon GO 박스의 보유 포켓몬 정보를 영상에서 추출해 검색 가능한 목록으로 저장 |
| 2차 목표 | 특정 레이드 보스에 대해 **현재 보유 상태**의 최대 화력 파티 6마리 추천 |
| 추천 철학 | **화력 우선**. 방어·안정성 중심 추천 모드는 만들지 않음 |
| 사용 데이터 | 현재 CP, IV 및 추정 레벨, 실제 보유 기술, 타입, 그림자 여부 등 |
| 육성 가정 | 강화, 진화, 기술머신 사용, 사탕 소비 등 **미래 상태 가정은 사용하지 않음** |
| 메가진화 | **기본 OFF**. 사용자가 체크하면 현재 활용할 수 있는 메가진화·원시회귀를 후보에 포함 |
| 날씨 | Pokémon GO 게임 내 날씨를 사용자가 선택하고 보정 계산에 반영 |
| 수집 방식 | **1차는 아이폰 화면 녹화 업로드**, 이후 필요하면 실시간 수집 확장 |
| 배포 방식 | 초기에는 맥에서 로컬 서버 구동 + 아이폰 사파리 웹앱 접근 |
| 서버 | 공개 서버·로그인·멀티유저 시스템 불필요 |
| AI 활용 | 이미지 해석 보조, 명칭 교정, 추천 근거 설명. **순위 숫자는 전투 계산 로직이 산출** |

### 0.2 해석을 분명히 할 부분

- **‘현재 보유 상태’**는 레이드 참가 전 추가 강화·진화·기술 변경을 하지 않는다는 뜻이다. 단, 메가진화 체크박스를 켜는 경우에만 **현재 사용 가능한 메가진화**를 가정해 전투 상태를 계산한다.
- **메가진화 가능 종**과 **현재 그 개체를 메가진화시킬 수 있음**은 다르다. 개체의 메가진화 경험·메가레벨·에너지·쿨다운을 별도로 관리해야 한다.
- **CP만으로는 화력이 결정되지 않는다.** 레벨, 개체값, 종족 공격력, 기술 성능, 보스 방어력과 타입 상성을 함께 사용한다.
- **사탕·XL사탕·별의모래·메가에너지 등은 박스 관리 관점에서 저장**하되, 2차 기능의 기본 레이드 순위에 '육성 후 가정'을 넣지는 않는다.
- **다이맥스·거다이맥스 여부는 1차 수집/목록에 포함할 수 있지만**, 맥스배틀 전용 파티 추천은 별도 전투 규칙이므로 일반 레이드 추천과 섞지 않고 후속 단계에서 다룬다.

## 1. 문제 정의 및 목표

### 1.1 현재 불편한 점

1. 포켓몬 GO 게임의 보관함은 여러 포켓몬의 **개체값, 기술, CP, 특수 형태, 자원**을 한 화면에서 비교하기 어렵다.
2. 한 포켓몬의 정보도 한 화면에 모두 나타나지 않는다. 이름·CP·사탕을 보는 화면, 스크롤 후 기술 화면, 메뉴를 통해 여는 **조사(IV) 화면**이 분리되어 있다.
3. 메가진화·다이맥스·거다이맥스 관련 상태는 개체별 추가 정보가 필요할 수 있다.
4. 게임 내 자동 추천 파티는 사용자가 원하는 **순수 화력 중심 평가**와 다를 수 있다.
5. 새로운 레이드가 등장할 때마다 “내가 현재 가진 포켓몬 중 어떤 6마리를 쓰는 것이 좋은가?”를 반복해서 판단해야 한다.
6. 많은 개체를 일일이 엑셀에 입력하는 과정 자체가 번거롭다.

### 1.2 제품 목표

**목표 A — 내 포켓몬 박스의 디지털 복제본**
- 포켓몬을 여러 화면에 걸쳐 촬영하더라도 **한 개체의 정보로 합쳐 저장**한다.
- 이름, CP, IV, 현재 기술, 특수 상태를 테이블·카드로 한눈에 볼 수 있다.
- 누락/오인식 정보를 수정하고, 같은 종의 여러 개체를 별도로 관리할 수 있다.

**목표 B — 현재 보유 포켓몬만을 이용한 최대 화력 추천**
- 레이드 보스·폼, 게임 내 날씨, 메가진화 옵션을 입력받는다.
- 6마리 각각의 현재 기술 구성을 기준으로 공격 효율을 계산한다.
- 추천 결과를 순위, 예상 화력 수치, 기술, 타입 상성, 적용 보정과 함께 보여준다.

### 1.3 비목표(초기 범위 제외)

- 남의 포켓몬/전 세계 최고 개체 기준 추천.
- 사탕·별의모래를 소비한 **강화 후** 시뮬레이션.
- 기술머신·대단한 기술머신을 쓴다는 가정의 **기술 변경 후** 추천.
- 진화하거나 정화한 뒤의 성능 예측.
- PvP(GO 배틀리그) 최적화.
- 멀티유저, 회원가입, 결제, 커뮤니티, 계정 공유.
- Pokémon GO 게임 로그인/서버 접속/내부 데이터 읽기/게임 자동 조작.
- 시작 단계에서 완전 자동 실시간 수집이나 앱스토어 배포.

## 2. 사용자 시나리오

### 2.1 초기 전체 수집

1. 아이폰에서 Pokémon GO를 실행하고 보관함을 연다.
2. **기본 상세 화면 → 필요한 만큼 아래로 스크롤해 기술 표시 → 조사 화면 → 다음 포켓몬** 순으로 보여 주며 화면을 녹화한다.
3. 화면 녹화 파일을 웹앱으로 업로드한다.
4. 분석기가 화면 상태를 인식하고 개체별 임시 기록을 만든다.
5. 이름·CP·기술·IV 등 인식값과 원본 근거 프레임을 검토한다.
6. 누락·충돌·낮은 신뢰도의 항목을 수정한다.
7. 확인된 포켓몬만 개인 DB에 저장한다.
8. 목록에서 검색·필터·정렬하며 확인한다.

### 2.2 추가 포켓몬/변경 사항 업데이트

1. 새로 잡거나 기술이 바뀐 포켓몬만 다시 녹화한다.
2. 기존 기록과 **일치 후보**를 제시한다.
3. 신규 등록인지 기존 개체 수정인지 사용자가 승인한다.
4. 변경 이력을 보관하고 기존 자료를 업데이트한다.

> **주의:** 게임 내 포켓몬의 영구 식별자(ID)를 공식 API로 받을 수 있는 구조가 아니다. 이름·CP가 같은 포켓몬도 여러 마리 존재할 수 있으므로 **완전한 자동 중복 판정은 보장할 수 없다.** 앱 자체 UUID와 사용자 확인 절차가 필요하다.

### 2.3 레이드 추천

1. 레이드 보스(정확한 폼 포함)를 선택한다.
2. `메가진화 포함` 체크박스는 기본적으로 해제되어 있다.
3. Pokémon GO 게임에 표시된 날씨를 선택한다. 기본값은 `날씨 보정 없음/미선택`.
4. `현재 파티 추천`을 실행한다.
5. 현재 등록된 포켓몬에서 실제 기술과 상태를 기준으로 계산한 추천 6마리를 확인한다.
6. 개별 포켓몬에 **선정 이유, 현재 기술, 예상 DPS, 상성 및 날씨 보정**을 표시한다.
7. 메가진화 체크를 켜면 메가·원시 형태를 포함해 다시 산정한다.

### 3.2 기술 스택

| 영역 | 1차 제안 | 이유 |
|---|---|---|
| 개발 머신 | Mac | 개발 및 로컬 추론·영상 분석 환경 |
| 언어/백엔드 | Python + FastAPI | OpenCV/OCR/영상 처리 파이프라인 연결이 쉽다 |
| 이미지·영상 | OpenCV + FFmpeg | 프레임 추출, 컷 탐지, 크롭, 이미지 정합 |
| 텍스트 인식 | OCR 라이브러리 + 필요 시 비전 모델 | 수치·한글 기술명·화면 제목 인식 |
| IV 인식 | 고정 영역 검출 + 막대 길이 추정 | 공격/방어/HP의 0~15 막대값 추출 |
| DB | SQLite | 단일 사용자·로컬 환경에 충분 |
| 프론트엔드 | React 또는 간단한 서버 렌더링 웹 | 모바일·맥 겸용 목록/업로드/결과 UI |
| 접속 | 동일 Wi-Fi의 로컬 IP | 초기에는 배포·운영 비용 최소화 |
| 파일 보관 | 로컬 폴더 | 원본 영상·근거 프레임 별도 저장 |
| AI | 선택적 로컬/외부 비전·LLM | 인식 오류 보조 및 설명용. 필수 의존성은 아님 |

**기술 선택은 권고안이지, 현재 구현된 상태가 아니다.** Java/Spring으로 백엔드를 만들 수도 있지만, 영상 처리 PoC는 Python으로 먼저 시작하는 편이 빠르다. 이 단계에서 백엔드를 이중화할 필요는 없다.

### 3.3 설치·실행 전략

- 초기에는 네이티브 iOS 앱 없이 **아이폰 사파리에서 개인 웹앱 접속**.
- 홈 화면 추가 기능을 사용하면 앱과 비슷한 진입 경험을 제공할 수 있다.
- **Mac 로컬 서버 방식은 맥이 켜져 있고 실행 중이며 아이폰에서 접근 가능한 네트워크여야 한다.**
- 맥이 꺼진 상태에서도 어디서든 사용하려면 추후 클라우드/상시 서버로 배포해야 한다.
- 화면 녹화 업로드는 iOS 사진 앱/파일 앱에서 파일 선택으로 처리한다.
- 실시간 스트리밍은 iOS 화면 방송/캡처 권한과 네이티브 구현이 필요할 수 있어 초기 범위에서 제외한다.
- 앱스토어 출시, TestFlight, Apple 개발자 유료 계정은 **웹앱 MVP에는 필요 없다.**

### 3.4 보안 및 게임 이용 정책

- Pokémon GO 계정의 로그인 정보·토큰을 수집하거나 저장하지 않는다.
- 비인가 게임 서버 API, 클라이언트 메모리 읽기, 패킷 후킹, 자동 클릭/스와이프를 구현하지 않는다.
- 사용자가 **직접 녹화한 화면을 사후 분석하는 방식**으로 시작한다.
- 화면 녹화·서드파티 도구 사용에 관한 게임 정책을 개발·사용 시점에 재확인한다. 화면 분석이 무조건 허용된다고 단정하지 않는다.
- 로컬이라도 외부에서 접근할 수 있는 포트 노출은 막고, 모바일에서 맥으로 전송할 때는 동일 LAN 또는 안전한 네트워크만 사용한다.
- 원본 영상에 닉네임·알림·기타 개인정보가 포함될 수 있으므로 보관 기간과 삭제 버튼을 마련한다.

## 4. 화면 녹화 기반 데이터 수집 설계

### 4.1 가장 어려운 부분: 여러 화면을 하나의 개체로 합치기

한 포켓몬의 상세 정보는 하나의 화면에 전부 표시되지 않는다. **가로 이동은 개체 변경, 세로 이동은 동일 개체의 추가 정보**라는 기본 가정을 사용하되, 영상에서 실제 UI 변화도 확인해야 한다.

```text
[포켓몬 A - 상단/기본 정보]
          │ 세로 스크롤
          ▼
[포켓몬 A - 기술/사탕/하단 정보]
          │ 조사 메뉴
          ▼
[포켓몬 A - 공격/방어/HP IV]
          │ 조사 닫기 + 가로 스와이프
          ▼
[포켓몬 B - 기본 정보]
```

**중요:** 이 순서는 사용자의 목표 녹화 절차다. 실제 메뉴 위치·표시 화면·스와이프 방향은 현재 게임 클라이언트에서 샘플로 확인해야 한다.

### 4.2 수집 파이프라인 상세

1. **영상 입력:** `.mp4`, `.mov` 지원. 해상도·FPS·회전 정보를 메타데이터로 저장.
2. **프레임 후보 추출:** 일정 간격 추출 + 화면 변화량/안정 구간 탐지. 무조건 매 프레임 OCR하지 않는다.
3. **프레임 품질 필터링:** 전환 애니메이션, 모션 블러, 메뉴가 겹친 화면, 흐릿한 장면 제외.
4. **화면 유형 분류:** `DETAIL_TOP`, `DETAIL_MOVES`, `APPRAISAL`, `MEGA_DETAIL`, `MAX_DETAIL`, `TRANSITION`, `UNKNOWN` 등.
5. **영역 검출:** CP/HP/이름/사탕/기술/IV 막대 등 분석할 위치를 탐색하고 크롭.
6. **OCR·이미지 분석:** 텍스트·숫자 인식; IV 막대 측정; 그림자·정화·맥스 배지 등 아이콘 검출.
7. **개체 세션 추적:** 동일 개체의 시간적으로 이어진 프레임을 묶음. 가로 스와이프·기본 화면 변경·조사 대상 전환을 함께 감지.
8. **필드별 신뢰도 산출:** `value`, `confidence`, `source_frame`, `source_region` 저장.
9. **충돌 판정:** 서로 다른 프레임의 이름/CP/기술이 모순되면 자동 병합 중단.
10. **임시 결과 표시:** 개체별 수집 완료/미수집 필드, 낮은 신뢰도 경고.
11. **사용자 확인:** 오인식 정정, 누락된 정보 수동 입력, 합치기/분리하기.
12. **DB 커밋:** 승인된 개체를 안정적인 앱 내부 UUID로 저장.

### 4.3 화면 유형별 수집 대상

| 화면/영역 | 추출 후보 | 주의점 |
|---|---|---|
| 상세 상단 | 이름, 폼, CP, HP, 외형·상태 아이콘 | 닉네임과 실제 종 이름 구분, 특수 폼 구분 |
| 상세 중단 | 강화 관련 표시, 사탕, XL사탕, 별의모래 관련 정보 | 보유 자원과 강화 **비용**을 구별 |
| 상세 하단 | 노말어택, 스페셜어택 1·2, 기술 타입 | 스크롤 필요, 잠금/미해금 기술칸 주의 |
| 조사(IV) | 공격/방어/체력 막대 | 별 0~4개 등급만으로는 0~15의 정확한 값 대체 불가 |
| 메가 관련 | 메가 가능 여부, 현재 레벨·에너지·쿨다운 | 개체별 메가레벨과 종별 자원 분리 |
| 맥스 관련 | 다이맥스/거다이맥스 개체 여부, 맥스기술·레벨 | 별도 화면/탭이 필요할 수 있음 |
| 전체 플레이어 자원 | 별의모래 등 | 개체 고유 값이 아니므로 별도 스냅샷 저장 |

### 4.4 IV 막대 인식 방식

- 조사 화면의 공격/방어/HP 영역을 감지한다.
- 각 막대의 색상이 채워진 길이를 기준으로 0~15 정수값을 추정한다.
- 프레임 확대/안티앨리어싱/해상도별 오차를 검증한다.
- **별 3개/4개** 등급은 보조 검증용으로만 사용한다.
- 공격/방어/HP 각 항목별로 별도 `confidence`를 남긴다.
- IV가 애매하면 `14 또는 15`로 임의 확정하지 말고 사용자 검토로 보낸다.

### 4.5 레벨 추정

- Pokémon GO 상세 UI에 정확한 포켓몬 레벨이 명시적으로 표시되지 않을 수 있다.
- `종족값 + CP + HP + IV + 현재 게임의 CPM(레벨별 보정계수) 표`로 **가능한 레벨 후보**를 계산한다.
- 후보가 여러 개면 추가 UI 지표 또는 사용자 확인이 필요하다.
- 원본 데이터에는 `level_estimate`, `level_confidence`, `estimation_method`와 같은 필드를 두어 **측정값과 추정값을 구분**한다.
- 추정 불가/모호한 개체를 고정 레벨로 가정하여 조용히 추천하지 않는다.

### 4.6 서로 다른 개체의 잘못된 병합 방지

**금지할 단순 판정:** `포켓몬 이름 + CP`만 같으면 같은 개체라고 처리하기.

권장 원칙:

- 최초 수집에서는 영상의 **시간상 연속된 포켓몬 세션**을 우선 단위로 사용.
- 이름/종/폼/CP/HP/IV/기술/그림자·반짝반짝 여부를 일치 후보에 활용.
- 다른 영상과의 비교 시 동일 후보가 여러 마리이면 **자동 덮어쓰기 금지**.
- `신규 개체 등록 / 기존 개체 업데이트 / 다른 개체로 분리 / 보류`를 사용자에게 제공.
- 앱 내부 UUID는 외부 게임 ID가 아니므로 사용자 확인 없이 영구 동기화가 가능한 것처럼 취급하지 않는다.

### 4.7 수집 완료의 정의

필수 항목(초기 레이드 추천용):

- [ ] 종/폼 식별
- [ ] 현재 CP, HP
- [ ] 공격/방어/체력 IV 또는 정확한 레벨 추정에 필요한 정보
- [ ] 실제 노말어택
- [ ] 실제 스페셜어택(1개 이상, 두 번째 존재 시 함께)
- [ ] 그림자 여부 및 추천에 영향을 주는 특수 전투 상태
- [ ] 메가진화 옵션을 적용하려면 해당 개체의 메가 사용 가능 상태
- [ ] 인식 결과가 사용자에 의해 승인됨

별도 관리(박스 UX용): 사탕·XL사탕·메가에너지·맥스 기술·별의모래 등.

`READY_FOR_RAID`, `PARTIAL`, `NEEDS_REVIEW` 상태를 구분한다. **필수 정보 누락 개체는 정확한 화력 순위에서 제외하거나 명시적 경고를 표시**한다.

## 5. 녹화 프로토콜 — 사용자가 따라 할 절차

### 5.1 최초 PoC 녹화 가이드

1. 아이폰에서 Pokémon GO를 연다.
2. 가능하면 화면 회전·텍스트 크기·확대 상태를 일정하게 유지한다.
3. **서로 다른 종 3마리 + 같은 종 2마리** 정도를 먼저 선정한다. 가능하면 그림자 또는 메가 가능한 개체도 포함한다.
4. iOS 화면 녹화를 시작한다.
5. 포켓몬 A 상세 상단에서 잠깐 멈춰 이름·CP가 선명하게 보이도록 한다.
6. 아래로 내려 사탕·기술이 전부 보이게 한다.
7. 조사 화면을 열고 IV 막대가 선명한 구간을 보여 준다.
8. 다음 포켓몬으로 넘어간 뒤 같은 과정을 반복한다.
9. 녹화를 마치고 영상 파일을 업로드한다.
10. 실제 추출 결과를 보면서 **게임 화면에 없는 정보와 놓친 정보**를 확인한다.

※ **‘몇 초씩 멈춘다’는 기준은 PoC 측정 후 정한다.** 초기부터 고정된 동작 속도를 사용자에게 강제하지 않는다.

### 5.2 스캔 단위 제안

| 단계 | 규모 | 목적 |
|---|---:|---|
| 샘플 | 5마리 | 화면 구조·인식 가능 필드 확인 |
| PoC | 10마리 | 기본/스크롤/조사 연결 및 개체 경계 확인 |
| MVP 검증 | 20~30마리 | 서로 다른 폼·기술·동일 종 중복·영상 길이 검증 |
| 확장 검증 | 수십~수백 마리 | 긴 영상, 중단/재개, 중복·증분 스캔 성능 확인 |

### 5.3 영상 촬영 실패 조건

- 이름과 CP가 흐릿해 읽히지 않는 상태에서 바로 다음 포켓몬으로 이동.
- 기술 영역까지 스크롤하지 않아 기술이 영상에 한 번도 나타나지 않음.
- 조사 화면의 IV 막대가 전환 애니메이션에 가려진 채 넘어감.
- 포켓몬 A의 조사 화면 이후 B의 상세 화면으로 넘어가는 경계가 불명확함.
- 영상에 없는 기술/에너지·폼 정보를 AI가 임의로 만들어 채움.

이런 경우에는 **추가 촬영 요청 또는 수동 보정**이 정답이며, 잘못된 값을 확정해서는 안 된다.

## 6. 보유 포켓몬 데이터 설계

### 6.1 반드시 분리할 데이터 계층

1. **종·폼 기준 데이터(`species_form`)**: 도감번호, 종 이름, 폼, 타입, 종족값, 메가 가능 형태, 게임 버전별 기술 목록 등.
2. **개체 데이터(`owned_pokemon`)**: 내가 실제로 가진 각각의 포켓몬. UUID, CP, HP, IV, 현재 기술, 그림자/반짝반짝 여부 등.
3. **진화 계열/종 공유 자원(`family_resources`)**: 사탕/XL사탕/메가에너지 등 해당 기준으로 공유되는 자원의 최신 스냅샷.
4. **개체별 메가 상태(`mega_state`)**: 메가진화 경험, 메가레벨, 쿨다운/가능 여부 등.
5. **개체별 맥스 상태(`max_state`)**: 다이맥스/거다이맥스 능력, 맥스 기술과 레벨.
6. **수집 세션과 근거(`scan_session`, `observations`)**: 영상 파일, 시각, 프레임, 신뢰도, 검토 여부.
7. **레이드 보스·전투 데이터(`raid_boss`, `moves`, `game_data_version`)**: 계산에 사용하는 기준 데이터.

### 6.2 개체 필드 정의

| 필드 | 예시 | 규칙 |
|---|---|---|
| `id` | UUID | 앱 내부 불변 식별자 |
| `species_id` | 도감번호 또는 내부 키 | 종 참조 |
| `form_id` | 기본/오리진/다른 폼 | 폼이 다르면 화력·타입이 달라질 수 있음 |
| `nickname` | 사용자 지정 이름 | 종 이름과 구분 |
| `cp` | 3192 | 원본 화면에서 읽은 현재 CP |
| `hp` | 160 | 원본 HP, 확인 가능할 경우 |
| `iv_attack`, `iv_defense`, `iv_stamina` | 15, 14, 15 | 각각 0~15 |
| `level_estimate` | 35.0 | 추정/확정 구분 필요 |
| `fast_move_id` | 기술 키 | 현재 보유 노말어택 |
| `charged_move_1_id`, `charged_move_2_id` | 기술 키 또는 `null` | 실제 보유 기술만 입력 |
| `is_shadow` / `is_purified` | `true/false` | 별도 플래그 |
| `is_lucky`, `is_shiny` | `true/false` | 관리용 속성. 화력에 직접 영향 없음 |
| `is_best_buddy_boost_active` | `true/false/unknown` | 실제 부스트가 활성 상태인지 별도 확인 |
| `mega_state_id` | FK/null | 해당 개체의 메가 상태 |
| `max_state_id` | FK/null | 해당 개체의 맥스 상태 |
| `collection_status` | `READY_FOR_RAID` 등 | 필수 정보 충족 및 검토 상태 |
| `last_scanned_at` | ISO 8601 | 마지막 화면 인식 시각 |
| `last_verified_at` | ISO 8601 | 마지막 사용자 확인 시각 |

### 6.3 자원 데이터

- 사탕/XL사탕: 진화 계열 공유 자원. 게임 내 표시 구조와 예외는 실제 화면으로 검증.
- 메가에너지: 해당 메가진화의 자원 보유량 및 개체별 첫 진화/재진화 비용 관련 상태 구분.
- 별의모래: 플레이어 전체 자원. **포켓몬별 보유 별의모래로 잘못 저장하지 않는다.**
- 맥스 파티클: 플레이어 공통 자원. 맥스기술 레벨은 각 개체 정보.
- 자원은 여러 영상에서 반복 등장할 수 있으므로 `resource_key + observed_at + source`로 스냅샷을 관리하고 최신값만 UI에 대표 표시한다.

### 6.4 메가진화/원시회귀 상태

| 필드 | 설명 |
|---|---|
| `eligible_forms[]` | 메가 X/Y 등 가능한 형태 목록 |
| `mega_evolved_before` | 이 **개체**가 이전에 메가진화한 적 있는지 |
| `mega_level` | Base/High/Max/Super Max 등 현재 시스템에 맞는 레벨 |
| `mega_energy_available` | 공용 자원 스냅샷 참조 |
| `energy_cost_now` | 현재 이 개체의 진화에 필요한 에너지(인식/계산) |
| `cooldown_ready_at` | 재메가진화 가능 시각 또는 재사용 가능 상태 |
| `can_activate_now` | 현재 에너지/쿨다운 등으로 실제 활성화 가능 여부 |
| `bonus_move_rules` | 추가 스페셜 어택이 있을 경우 전투 상태 생성 규칙 |

**메가진화를 실제로 해보지 않고도** 종별 메가 종족값을 사용해 *추정 전투 CP/화력*을 계산할 수 있다. 다만 현재 진화 가능 여부·메가레벨은 화면에서 확인하지 못하면 불명확할 수 있다.

### 6.5 저장 구조 예시

```json
{
  "id": "app-generated-uuid",
  "species": "샹델라",
  "form": "NORMAL",
  "cp": 3192,
  "hp": null,
  "ivs": {"attack": 15, "defense": 14, "stamina": 15},
  "level_estimate": null,
  "moves": {"fast": "회오리불꽃", "charged": ["오버히트"]},
  "flags": {"shadow": false, "purified": false, "lucky": false},
  "mega": null,
  "max": {"type": "NONE"},
  "collection_status": "NEEDS_REVIEW",
  "field_confidence": {"cp": 0.99, "fast_move": 0.95, "iv_attack": 0.88}
}
```

> 위 값은 **데이터 구조를 보여주는 예시**이며 실제 보유 포켓몬 기록이 아니다.

## 7. 내 포켓몬 박스 화면 요구사항

### 7.1 목록 화면

- 카드·표 전환. 모바일에서는 카드 우선, 맥에서는 밀도 높은 테이블을 제공.
- 한 줄/카드에 `포켓몬 이름/폼`, `CP`, `IV 15/14/15`, `현재 기술 2~3개`, `그림자`, `메가 가능`, `다이맥스/거다이맥스` 표시.
- 검색 대상: 종/닉네임/기술/폼.
- 정렬: CP, 공격 IV, IV 합계, 종 이름, 마지막 업데이트, 예상 범용 공격 화력 등.
- 필터: 타입, 그림자, 메가, 다이맥스, 거다이맥스, 보유 기술, 인식 보류 여부.
- 동일 종의 여러 개체를 나란히 비교.
- `스캔 누락`, `사용자 검토 필요`, `레이드 계산 가능` 배지.
- 각 개체에서 근거 프레임을 확인할 수 있는 `원본 보기`.

### 7.2 상세 화면

```text
샹델라                     CP 3192
불꽃/고스트    IV 15 / 14 / 15

현재 기술
- 노말: 회오리불꽃
- 스페셜: 오버히트
- 두 번째 스페셜: 없음

상태
- 그림자: 아니오
- 메가진화: 해당 없음
- 다이맥스: 해당 없음

마지막 스캔: YYYY-MM-DD
인식 신뢰도: [필드별 보기]
[정보 수정] [원본 프레임] [삭제]
```

### 7.3 수집 관리 화면

- 영상 업로드, 분석 상태, 성공/보류/실패 수.
- 포켓몬별로 인식한 필드와 누락된 필드 시각화.
- 충돌 후보 비교: `새 개체 등록`, `기존 기록과 합치기`, `분리`, `보류`.
- 원본 프레임·텍스트 크롭 함께 보여주기.
- 정정 내역과 수정 전후 기록.
- 기존 포켓몬을 삭제하지 않고 영상 세션만 폐기하는 기능.

## 8. 레이드 추천 기능 상세 요구사항

### 8.1 레이드 종류 구분

| 콘텐츠 | 파티 | 기본 구현 |
|---|---|---|
| 일반/전설/그림자 등 일반 레이드 | 통상 6마리 | **2차 핵심 기능** |
| 메가 레이드 | 통상 6마리 | 일반 레이드 화력 규칙과 보스 폼 차이 적용 |
| 슈퍼 메가 레이드 등 특수 이벤트 | 이벤트별 고유 규칙 | 별도 규칙 확인 후 지원. 일반 레이드와 동일 취급 금지 |
| 다이맥스/거다이맥스 맥스배틀 | 3마리, 맥스 전용 규칙 | **후속 개발** |

### 8.2 추천 입력값 — 최소 UI

**반드시 표시하는 입력값은 3개만 둔다.**

1. **레이드 보스 선택**: 종, 정확한 폼/레이드 종류 자동 연결.
2. **메가진화 포함**: 체크박스, 기본 `OFF`.
3. **날씨**: 게임 내 날씨 선택, 기본 `보정 없음`.

초기에는 친구 보너스, 파티 파워, 날씨 자동 위치 연동 같은 추가 설정을 강제하지 않는다.

### 8.3 레이드 설정 예시

```text
[레이드 보스]  뮤츠 (일반 형태)      [검색/선택]
[ ] 메가진화 포함                 ← 기본 OFF
[날씨]         보정 없음           [선택]

[현재 보유 포켓몬으로 파티 추천]
```

### 8.4 결과 화면

- 1위부터 6위까지 포켓몬별 `이름`, `폼`, `CP`, `현재 기술`, `예상 DPS`, `유리한 기술 타입`, `상성 보정`, `날씨 보정` 표시.
- 메가진화 체크 시 실제 추천된 메가·원시 형태를 명시하고 **해당 전투 상태에서의 예상 CP/기술/화력**을 표시.
- 총 6마리 조합의 예상 공격 기여도 요약. 단순 개인별 DPS 합과 시간에 따른 실전 총딜은 구별.
- `계산 데이터 버전`, `계산 가정`, `미확인 항목` 보기.
- 데이터가 부족하면 정확도 경고 또는 계산 제외를 표시하고, AI가 그럴듯한 숫자를 임의 생성하지 않도록 한다.

### 8.5 추천 순위 정책

- **주 평가 목표: 현재 상태에서의 레이드 보스 상대 공격 DPS.**
- 후보 개체는 보유 DB의 `READY_FOR_RAID` 개체로 제한한다.
- 각 개체는 현재 기술만 사용한다. 스페셜어택이 2개면 **실제 보유 중인 두 기술**을 활용할 수 있도록 계산한다.
- 후보 포켓몬 1마리는 파티의 한 자리에만 배치한다. 동일 종이라도 DB의 **서로 다른 실제 개체**라면 여러 자리에 포함 가능.
- 메가 체크 OFF: 메가/원시 형태를 생성하지 않는다.
- 메가 체크 ON: 현재 가능하다고 확인된 메가/원시 후보를 계산하고 **활성 메가/원시 제약**을 적용한다.
- 같은 보스에 대해 날씨가 변하면 기술 위력 보정이 달라지므로 순위를 다시 계산한다.
- 순수 화력 중심이며, 내구·TDO를 최우선으로 하지 않는다.

> **설계상 주의:** 전투 시간 동안의 공격 기여, 피격으로 인한 스페셜 에너지 생성, 기절과 재입장 등까지 포함하면 *실제 DPS*가 달라질 수 있다. MVP는 가정이 명시된 공격 사이클 기반 추정치를 제공하고, 고급 전투 시뮬레이션은 추후 정밀화한다.

## 9. 메가진화 옵션 설계 — 기본 OFF

### 9.1 UX 동작

**기본 동작**
- 아무것도 선택하지 않으면 일반 상태만으로 6마리 추천.
- 메가진화 가능한 포켓몬도 **메가진화하지 않은 현재 상태**로 계산.

**체크 활성화**
- 현재 메가진화/원시회귀가 가능한 개체만 변환 후보로 추가.
- 변환 후의 종족값, 타입, CP, 사용 가능한 기술을 반영.
- `한 번에 하나의 활성 메가진화` 등 현재 게임 제약을 적용.
- 메가·원시 후보와 일반 후보를 조합하여 결과를 다시 계산.
- 에너지/쿨다운/메가레벨을 확인하지 못한 개체는 **사용 가능 미확인**으로 구분.

### 9.2 왜 상태 분리가 필요한가?

- 메가진화 후 일부 포켓몬은 타입이 달라진다(예: 메가리자몽 X).
- 기본 종과 메가 종의 종족값이 달라 전투 CP 및 DPS가 달라진다.
- 현재 보유한 노말어택/스페셜어택은 보통 그대로 유지된다.
- **일부 특정 포켓몬은 메가진화 상태에서 추가 스페셜 어택을 사용할 수 있고, 그 추가 기술에 메가레벨별 위력 보정이 적용된다.**
- 모든 메가 포켓몬이 추가 공격을 얻는다고 가정하면 안 된다.

### 9.3 추가 스페셜 어택(2026년 기준 공식 도움말 확인)

공식 도움말은 특정 슈퍼 맥스 레벨 대상 메가진화 포켓몬이 **추가 스페셜 어택**을 사용할 수 있으며, 해당 추가 기술의 보너스 배율을 **Base 1.0 / High 1.1 / Max 1.2 / Super Max 1.3**으로 설명한다. 이 배율은 **추가 스페셜 어택 위력에 적용되는 값**이지, 모든 메가진화 기술에 무조건 곱하는 배율이 아니다.

**개발 요구사항**
- `mega_bonus_move`를 개체가 기본으로 기억한 스페셜어택과 구별한다.
- 해당 종/폼이 이 규칙을 적용받는지 게임 데이터로 확인한다.
- 메가레벨에 따라 해당 **추가 공격만**의 보정값을 적용한다.
- 기존 기술을 지우거나 메가 전용 기술을 영구 저장하지 않는다.
- 이 규칙의 적용 대상/사용 조건은 업데이트될 수 있으므로 데이터 기반으로 관리한다.

출처: [Pokémon GO 공식 도움말 — 메가진화](https://niantic.helpshift.com/hc/ko/6-pokemon-go/faq/3328-what-is-mega-evolution/?hl=e), [메가레벨](https://niantic.helpshift.com/hc/en/6-pokemon-go/faq/3331-how-can-i-increase-a-pokemon-s-mega-level/).

### 9.4 메가 레이드 팀 보너스

메가진화 포켓몬이 배틀 중일 때 다른 트레이너의 공격에 보너스를 주는 규칙이 있다. 하지만 **내 6마리 DPS를 정확히 계산하는 것과 동료에게 주는 보너스를 포함한 전체 레이드 팀 최적화는 다른 목표**다.

- MVP: **내 개체의 직접 공격력**을 기준으로 추천.
- 추후: 파티 인원·동시 전투·메가 보너스를 고려한 팀 전체 최적화 별도 제공 가능.
- 동일 보너스 중첩/적용 대상은 공식 규칙을 기준으로 별도 검증한다.

출처: [Pokémon GO 공식 도움말 — 메가진화 포켓몬 사용](https://niantic.helpshift.com/hc/en/6-pokemon-go/faq/3334-using-a-mega-evolved-pokemon/).

### 9.5 현재 메가진화 가능 여부가 모호할 때

단순히 메가 가능 종이라고 해서 자동으로 메가 모드 추천 후보에 넣지 않는다. 다음 상태를 둔다.

- `AVAILABLE`: 현재 에너지/무료 재진화 등으로 사용 가능함이 확인됨.
- `UNAVAILABLE`: 현재 사용 불가로 확인됨.
- `UNKNOWN`: 영상에 정보가 없어 알 수 없음.

기본 정책은 `AVAILABLE`만 실제 추천에 넣고, `UNKNOWN`은 검토 필요로 제시한다. 예외로 사용자가 직접 “현재 메가진화 가능”을 확인할 수 있다.

## 10. 날씨 보정 설계

### 10.1 핵심 원칙

- 날씨는 **실제 기상청 날씨가 아니라 Pokémon GO 게임에 적용된 날씨**를 사용한다.
- 사용자가 원격 레이드를 참여한다면 **레이드가 진행되는 게임 내 장소의 날씨**를 기준으로 입력해야 한다.
- 날씨 보정은 포켓몬 자신의 타입만으로 정하는 것이 아니라 **사용하는 공격 기술의 타입**을 기준으로 적용한다.
- 초기 기본값 `보정 없음`은 **해당 날씨를 모름/미적용**이라는 계산 모드다. 실제 현장의 날씨가 존재하지 않는다는 뜻은 아니다.

### 10.2 날씨별 강화 타입

| 비(Rainy) | 물, 전기, 벌레 |
| 약간 구름(Partly Cloudy) | 노말, 바위 |
| 흐림(Cloudy) | 페어리, 격투, 독 |

## 11. 화력 계산 엔진

### 11.1 왜 단순 CP 정렬로는 안 되는가?

- CP는 여러 능력치를 종합한 지표이므로 **실제 공격 효율을 직접 표현하지 않는다.**
- 실전 화력은 종족 공격력, IV 공격, 레벨, 사용하는 기술의 PvE 위력·시전 시간·에너지, 공격 기술 타입과 보스 상성에 달려 있다.
- 같은 CP라도 기술이 다르면 DPS 차이가 커질 수 있다.
- 그림자 포켓몬은 공격 보정 때문에 일반 개체보다 높은 화력을 낼 수 있다.
- 날씨/자속/타입 상성이 누적되면 기본 CP만으로 추천 순위가 맞지 않을 수 있다.

### 11.2 필수 계산 입력

**내 포켓몬**
- `species_form_id`, 종족 공격력, 현재 레벨 또는 신뢰 가능한 레벨 추정, 공격 IV.
- 현재 노말어택과 스페셜어택 1·2.
- 기술의 레이드/PvE 전용 위력, 공격 시간, 에너지 획득·소비.
- 현재 그림자 여부, 사용자가 메가 옵션을 켰을 때 현재 사용 가능한 메가 형태.

**레이드 보스**
- 정확한 보스 종/폼, 타입, 레이드용 방어 수치 및 난이도에 따른 조건.
- 보스가 사용하는 기술이 알려진다면 추가 분석 가능. 단, MVP 필수 입력으로 요구하지 않음.

**환경**
- 게임 내 날씨.
- 레이드 계산 규칙 데이터 버전.
- 메가진화 체크 상태.

### 11.3 기본 보정 요소

| 항목 | 개념 | 기본 처리 |
|---|---|---|
| 타입 상성 | 효과가 굉장함/별로/이중 상성 | 기술 타입과 보스 각 타입으로 계산 |
| 자속(STAB) | 포켓몬 타입과 기술 타입이 일치 | 기술별로 판정 |
| 그림자 | 공격력 증가 | 해당 개체에만 적용 |
| 날씨 | 특정 기술 타입 보정 | 선택한 게임 날씨 적용 |
| 메가/원시 | 전투 종족값·타입·추가 기술 변화 | 옵션 활성 시에만 적용 |
| 레벨·IV | 실전 공격 능력치에 반영 | 정확도 부족 시 검토 필요 |
| 기술 에너지/시간 | 연속 공격 사이클에 직접 영향 | PvE 데이터를 사용 |

널리 사용되는 Pokémon GO PvE 상수에는 `단일 약점 1.6배`, `이중 약점 2.56배`, `자속 1.2배`, `그림자 공격 보정 1.2배` 등이 있다. **실제 코드에서는 하드코딩된 암기값이 아니라 관리·검증 가능한 게임 데이터/계산 규칙 모듈을 단일 진실 공급원으로 사용한다.**

### 11.4 추천 계산의 개념 흐름

```text
입력: 보스 B, 날씨 W, 메가 체크 M

1) 게임 데이터 버전 선택
2) 내 포켓몬 중 필수 정보 확인된 후보 조회
3) 후보마다 전투 상태 생성
   - M=OFF: 일반 상태만
   - M=ON: 일반 상태 + 현재 가능한 메가/원시 상태
4) 각 상태에 대해
   - 실제 보유 기술 집합 계산
   - PvE 기술 데이터 로드
   - 보스 타입 상성 적용
   - STAB/그림자/날씨/해당 추가 기술 보정 적용
   - 기술 시전시간·에너지 순환을 반영한 DPS 계산
5) 동일 개체는 하나의 상태만 선택
6) 메가/원시 활성 제약 준수
7) DPS가 높은 6개 개체 조합 선택
8) 결과와 각 보정 근거 출력
```

### 11.5 구현 단계별 정밀도

**Level 1 — 검증 가능한 공격 사이클 기반 DPS (MVP)**
- 노말기 반복과 스페셜기 사용을 반영한 기술 사이클 계산.
- 타입/날씨/그림자/STAB/메가 상태 반영.
- 현재 스페셜 기술이 2개인 포켓몬은 실전에서 가능한 활용 조합 비교.
- 명확한 가정을 UI에 표시: 보스 기술·회피·사망·재진입·친구 보너스·파티 파워는 미포함.

**Level 2 — 전투 시간 시뮬레이션 (선택적 후속)**
- 실제 보스 공격과 피격 에너지, 기술 애니메이션, 기절, 회피 등을 반영.
- 평균 DPS, 생존 중 총딜, 예상 전멸 등을 별도 계산.
- **생존 최적화 모드가 아니라 실전 화력 예측 정확도를 높이는 목적**으로만 도입.

### 11.6 데이터 갱신 전략

> 상세 데이터 출처·API 경로·해시 비교·버전 관리와 검증 절차는 **23~27장**을 참조한다.


- PvE 기술의 위력·시간·에너지 등은 게임 패치로 변경될 수 있다.
- `game_data_version`에 원본 출처, 가져온 날짜, 해시, 기술/종족값 테이블 버전을 기록한다.
- **PvP 기술 수치와 레이드(PvE) 수치를 섞지 않는다.**
- 데이터 소스가 불명확하거나 업데이트되지 않으면 `게임 데이터 최신 확인 필요` 경고.
- 공식적으로 제공되는 공개 게임 데이터 API가 있다는 가정으로 설계하지 않는다. 법적·라이선스 범위를 확인한 공개 자료/수동 검증 스냅샷을 검토한다.
- 향후 값이 바뀌면 기존 계산 결과를 새 버전으로 재계산할 수 있어야 한다.

### 11.7 AI의 역할과 책임 경계

**AI가 도움을 줄 수 있는 일**
- OCR 후보 중 기술명 교정(사전에 존재하는 기술만 허용).
- 불명확한 화면 영역 분류를 보조.
- 추천 결과 설명: “이 포켓몬은 고스트 타입 기술을 실제로 보유하며 뮤츠의 약점을 공략함.”
- 데이터가 누락된 개체의 재촬영 안내.

**AI에게 맡기지 않을 일**
- 근거 없이 IV/CP/기술을 만들어 내기.
- 전투 수치를 출처 없이 추측해 DPS 산출.
- 현재 보유하지 않은 기술을 있다고 가정하기.
- 강화·진화·기술변경을 자동 추천 파티에 섞기.

## 12. 다이맥스·거다이맥스 처리

### 12.1 초기 1차 수집 대상

- 해당 개체가 `NONE`, `DYNAMAX`, `GIGANTAMAX` 중 어느 상태인지.
- 실제 현재 보유 맥스기술과 레벨(별도 화면에서 확인 가능할 경우).
- 거다이맥스 여부는 **종이 아니라 개체 단위의 속성**으로 관리.
- 일반 레이드용 기술과 맥스배틀용 기술·기술 레벨을 섞지 않는다.

### 12.2 일반 레이드 추천과 분리하는 이유

- 맥스배틀은 일반 레이드와 다른 참가 가능 포켓몬, 파티 수, 전투 단계/맥스기술 규칙을 가진다.
- 일반 레이드 추천의 6마리 DPS를 그대로 맥스배틀 3마리 추천에 적용하면 부정확하다.
- 사용자가 원래 원한 “메가·다이맥스·거다이맥스 여부 한눈에 보기”는 1차 목록 기능으로 우선 달성.
- **맥스배틀 파티 추천은 별도 3차 기능으로 보류.**

## 15. 데이터 저장과 증분 동기화

### 15.1 최초 등록 후에는 전체 재스캔을 강제하지 않음

- 처음에는 보유 개체를 다량 등록할 수 있다.
- 이후 신규 개체·기술 변경·CP 변경 등만 수집하면 된다.
- 이미 등록된 포켓몬이 다시 보이면 일치 후보를 찾고 사용자 승인으로 업데이트한다.
- **같은 종/같은 CP/같은 IV의 서로 다른 개체**를 구별해야 하므로 추정만으로 덮어쓰지 않는다.

### 15.2 수정/이력

- 개체 정보의 이전 값 및 최종 수정 시각 기록.
- 수집 영상과 각 필드의 원본 프레임 연결.
- 수정 전·후를 비교할 수 있게 변경 로그 보존.
- 삭제는 사용자가 확인할 수 있도록 별도 동작 제공.

### 15.3 백업

- 로컬 SQLite 파일과 사용자 수정 데이터를 주기적으로 내보내기.
- JSON/CSV 내보내기로 추후 Google Sheets 등과 호환 가능.
- 데이터베이스 백업과 업로드한 동영상은 별도로 관리.
- 원본 영상 삭제 후에도 확정된 포켓몬 데이터는 유지하도록 구성.

## 17. 구현 로드맵

### Phase 0 — 샘플 확보·리스크 검증

**입력:** 직접 녹화한 포켓몬 5~10마리 영상.

작업:
- iPhone 화면 캡처 해상도와 상세/기술/조사 화면 레이아웃 확인.
- 각 화면에서 실제로 볼 수 있는 필드 목록 작성.
- OCR과 IV 막대 인식 가능한지 소규모 수작업 검증.
- 사용자 녹화 동선이 지나치게 번거롭지 않은지 확인.

**완료 기준:** 각 정보가 어느 화면에 나타나는지 확인되고, 한 개체의 화면을 수동/반자동으로 묶어 JSON 출력 가능.

### Phase 1 — 영상→개체 JSON PoC

작업:
- FFmpeg/OpenCV로 프레임 추출.
- 화면 유형 분류.
- 이름·CP·기술·IV 인식.
- 세로 스크롤/가로 개체 전환 인식.
- 개체별 세션 병합과 신뢰도 출력.

**완료 기준:** 10마리 샘플에서 각 개체별 레코드가 생성되고, 잘못 합쳐진 개체를 확인·수정할 수 있음.

### Phase 2 — 개인 박스 MVP

작업:
- SQLite 영속화.
- 업로드 UI, 스캔 결과 검토·수정.
- 목록/상세/검색/필터/중복 관리.
- 사탕/에너지 등 수집 가능한 자원 표시.
- 데이터 내보내기/백업.

**완료 기준:** 수집한 보유 포켓몬 20~30마리를 다시 입력하지 않고 목록에서 조회·수정·비교 가능.

### Phase 3 — 레이드 최대 화력 추천 MVP

작업:
- 폼/타입/기술/PvE 데이터 테이블 확보.
- 현재 개체 상태에서의 DPS 계산.
- 레이드 보스 선택.
- 메가진화 OFF 기본값 및 체크 ON 변환 계산.
- 날씨 선택 및 기술 타입 날씨 보정.
- 상위 6개체 추천과 근거 표시.

**완료 기준:** 보스/날씨/메가 옵션을 바꾸면 결과가 합리적으로 변하고, 기준 사례와 계산 결과를 대조 가능.

### Phase 4 — 품질 안정화 및 편의 기능

## 18. 인식 품질과 테스트 전략

### 18.1 테스트 데이터셋 구성

| 케이스 | 검증 항목 |
|---|---|
| 서로 다른 5종 | 종 이름/CP/기술 기본 인식 |
| 같은 종의 다른 개체 2마리 | 개체 경계 및 중복 처리 |
| CP가 같은 개체 2마리 | `이름+CP` 단순 병합 오류 방지 |
| 스페셜 기술 2개 보유 | 두 기술 모두 수집 |
| 그림자/정화 | 상태 아이콘 구분 |
| 메가 X/Y가 가능한 종 | 폼/메가 상태 분리 |
| 다이맥스/거다이맥스 개체 | 개체별 맥스 유형 구분 |
| 조사 화면 빠진 영상 | `NEEDS_REVIEW` 처리 |
| 기술 화면 빠진 영상 | 레이드 계산 준비 상태가 되지 않도록 차단 |
| 화면 전환이 빠른 영상 | 애니메이션·모션 블러 제외 |
| 게임 UI/언어 변경 | OCR 실패/지원 버전 안내 |

### 18.2 초기 품질 목표(합의할 목표치, 성능 보장 아님)

- 잘못된 포켓몬 간 자동 병합: **검수 샘플에서 0건 목표**.
- CP·기술·IV: 값이 애매하면 **자동 확정하지 않고 검토 요청**.
- 포켓몬별 모든 필수 필드가 확보됐는지 명확한 상태 표시.
- 결과 화면에 원본 프레임을 열어 **수정 가능한 근거** 제공.
- 20~30마리 영상으로 사람 손 입력 대비 절약되는 시간을 실측.
- 계산 순위는 고정 테스트 케이스에서 반복 실행해도 동일해야 함.

### 18.3 레이드 추천 검증 케이스

1. 같은 개체, 같은 보스에서 날씨 없음→강풍 변경 시 해당 타입 기술에만 날씨 보정.
2. 같은 개체에서 메가 OFF→ON으로 바꾼 경우, 가능한 개체만 전투 형태 변경.
3. 메가 체크 ON이어도 현재 사용할 수 없는 메가 후보는 임의 포함하지 않음.
4. 그림자 개체 공격 보정이 일반 개체와 다르게 계산됨.
5. 같은 CP의 두 개체라도 IV/기술이 다르면 비교 결과가 달라질 수 있음.
6. 보스 폼이 바뀌면 해당 타입/방어력 기준으로 재평가.
7. 상위 6마리는 **서로 다른 보유 개체 ID**이며 한 개체가 중복 배치되지 않음.
8. 두 번째 스페셜어택을 가진 개체는 실제 보유한 두 기술만 평가.
9. 분석 불완전 개체가 조용히 `0 DPS` 또는 가상의 기술로 추천되지 않음.
10. 게임 데이터 버전 변경 시 계산 결과를 재현/비교할 수 있음.

## 22. 다음 액션 — 가장 먼저 할 일

**첫 번째 작업은 애플리케이션 UI 제작이 아니라, 실제 게임 영상에 대해 ‘개체별 기록이 만들어지는가?’를 검증하는 것이다.**

권장 첫 순서:

1. 아이폰에서 포켓몬 **5마리**를 `상단 → 아래로 스크롤 → 조사 → 다음 포켓몬` 흐름으로 녹화한다.
2. 같은 종 2마리를 포함해 중복 개체 인식 문제를 일찍 검증한다.
3. 해당 영상에서 기본 정보·기술·IV의 정답값을 수작업으로 기록해 테스트 기준을 만든다.
4. Mac에서 간단한 Python 스크립트로 프레임 추출·화면 분류·OCR/IV 인식을 실행한다.
5. `scan_output.json`에 개체별로 읽힌 정보와 누락/신뢰도, 원본 프레임 경로를 저장한다.
6. 인식 실패한 필드와 UI 흐름을 분석해 PoC를 개선한다.
7. **이 과정이 안정화된 이후** SQLite 및 웹 목록 UI를 연결한다.
8. 레이드 계산 엔진은 사용자가 확인한 테스트 개체 데이터로 따로 검증한 후 연동한다.

### 첫 성공 화면의 정의

```text
스캔 세션: sample_001
총 개체 후보: 5

1. 샹델라 | CP 3192 | IV 15/14/15
   노말: 회오리불꽃 | 스페셜: 오버히트
   상태: 검토 완료

2. [다음 포켓몬] | CP ... | IV ...
   ...

누락 항목: 2건
중복 의심: 1건
[원본 화면 확인] [수정] [확정 저장]
```

> 위 화면 및 포켓몬 수치는 예시이다. 실제 샘플 스캔 결과가 아니다.

## 23. 공개 게임 데이터 조사 및 공급원 선택 (v1.1 신규)

### 23.1 공식 계정 데이터와 게임 기준 데이터는 다르다

**A. 내 개인 계정 데이터(별도 수집):** 보유 개체 ID(앱 내부 UUID), 화면에서 관찰한 CP/HP/IV/기술/폼/그림자/메가·맥스 상태/자원. 일반 개발자가 사용자 계정의 포켓몬 박스를 공식 공개 API로 일괄 조회하는 경로가 제공된다고 전제하지 않는다. 이 앱은 게임 서버를 직접 조회하거나 로그인 정보를 수집하지 않고, 사용자가 촬영한 화면만 분석한다.

**B. 게임의 공개·커뮤니티 기준 데이터(가져와 사용):** 포켓몬별 종족값·타입·폼, 기술별 PvE 위력·에너지 변화·시전 시간, 타입 상성·날씨·CPM(레벨 배율), 일부 메가진화 데이터. API/데이터셋은 **공식 Niantic/Scopely 보장 서비스가 아닌 제3자 출처**임을 표기한다.

**C. 기준 계산 결과/외부 시뮬레이션(검증에 활용):** 특정 레이드 상대 카운터 시뮬레이션 및 추천 순위를 제공하는 서비스. 우리의 계산 결과를 대조하는 용도이지, 사용자 박스의 모든 개체 순위를 다른 서비스의 티어표로 그대로 치환하지 않는다.

### 23.2 공급원 비교 및 권장 용도

#### 데이터 소스 선택 규칙

1. 첫 구현은 **PoGo API의 JSON을 로컬 캐시**하고, 필요한 필드만 내부 표준 모델로 변환한다.
2. 데이터 출처가 서로 다른 경우 **원본 값·출처·버전을 기록**하고 공식 규칙·게임 내 동작·검증 시뮬레이션과 비교한다.
3. 특정 기술/메가 폼이 소스에 없으면 0점으로 조용히 계산하지 않는다. `UNSUPPORTED_GAME_DATA` 또는 `STALE_GAME_DATA`로 표시하고 수동 검증 대상으로 분리한다.
4. 사용자 게임 데이터(스캔)와 기준 데이터(외부 JSON)를 분리한다. 기준 데이터를 업데이트해도 내 개체 원본 관측값은 덮어쓰지 않는다.
5. **PvE(레이드) 수치**와 **PvP(트레이너 배틀) 수치**는 테이블/키 차원에서 분리한다.

**API 응답 필드 예시(PvE 노말 기술):** 아래는 실제 문서의 구조를 설명하기 위한 예시다. 기술 위력·시전 시간 등은 패치에 따라 바뀌므로 현재 스냅샷의 숫자로 계산해야 한다.

```json
{
  "name": "Shadow Claw",
  "move_id": 213,
  "type": "Ghost",
  "power": 6,
  "duration": 500,
  "energy_delta": 4
}
```

- `power`: 기술 기본 위력 (최종 데미지 아님)
- `duration`: 기술 시간(ms), 레이드 서버의 공격·데미지 창 등 세부 모델은 정확도 향상 시 별도 고려
- `energy_delta`: 양수이면 생성, 음수이면 소비하는 에너지
- `move_id`: 데이터 소스에서 제공하는 식별값. 한국어 OCR 명칭보다 안정적인 내부 참조 키로 활용할 수 있지만 버전 호환성 확인
- 화면에 표시된 **한국어 기술명**을 영문 기술명·내부 키로 변환하는 다국어 사전은 별도로 관리한다.

**특별 주의:** `current_pokemon_moves.json`은 **현재 새로 배울 수 있는 기술 목록**이지 플레이어가 과거에 얻어 이미 보유한 모든 레거시 기술의 완전 목록을 뜻하지 않는다. 게임에 이미 보유한 기술을 OCR로 확인했다면 '현재 습득 목록에 없다'는 이유만으로 삭제하거나 오류 처리하지 않는다.

## 24. 레이드 화력 계산의 상세 명세 (v1.1 신규)

### 24.1 앱이 계산하는 'DPS'의 의미와 한계

- **MVP 기본:** 보스별 타입·능력치 및 보유 기술에 대한 **지속 공격 주기 기반 예상 DPS**. 공격자가 피격되는 상황·회피·기절·재진입·파티 파워를 제외한 이론값이다.
- **추후 고정밀:** 보스의 실제 기술, 공격 타이밍, 받은 피해에 따른 에너지 획득, 기절·재진입을 포함한 **시뮬레이션 실전 DPS**를 따로 보여줄 수 있다.
- 사용자에게 표시하는 수치에는 반드시 `계산 방식`, `게임 데이터 버전`, `날씨`, `메가 체크 상태`를 함께 기록한다.
- '레이드 추천 1위'는 이 계산 모델에서 최대 화력이라는 뜻이지, 모든 현장 상황에서 실측 1위라는 보장은 아니다.

### 24.2 전투 입력 모델

```text
OwnedPokemon (한 개체)
  species_id + form_id + pokemon_uuid
  level (추정치 및 오차 여부)
  atk_iv, def_iv, sta_iv
  current_cp, current_hp
  fast_move_id
  charged_move_1_id, charged_move_2_id?  # 실제로 해금되어 있을 때만
  is_shadow, is_purified, best_buddy_active?
  mega_evolution_history?, mega_tier?, mega_ready?

RaidContext
  boss_species_id, boss_form_id, raid_tier
  weather_code | NONE
  include_mega = false
  boss_fast_move_id? / boss_charged_move_id?  # 향후 고급 모드
  game_data_version
```

### 24.3 피해량 기본 모델과 배율

사용할 게임 버전과 기술 규칙에 대조해야 하는 **개념식**(일반 레이드 PvE 기본형):

```text
실제 공격능력 = (종족 공격 + 공격 IV) × 레벨별 CPM × 형태/버프에 따른 해당 보정
상대 방어능력 = (보스 종족 방어 + 적용 IV) × 보스 CPM × 특수 보정
기술별 피해량 = floor(0.5 × 기술 위력 × 공격능력/방어능력 × 배율 묶음) + 1
```

일반적인 배율 묶음의 후보:

| 요소 | 처리 | 테스트 |
|---|---|---|
| 공격 기술 타입 vs 보스 타입 | 타입별 상성 곱(이중 타입인 경우 두 타입에 각각 적용) | 약점/저항/중립/이중 약점 |
| STAB | 기술 타입이 **현재 전투 폼**의 타입 중 하나와 일치하면 보정 | 메가진화로 타입이 달라진 폼 테스트 |
| 그림자 상태 | 일반 상태와 별도 공격 피해 보정 | 그림자/정화/일반 혼합 테스트 |
| 날씨 | 게임 내 현지 날씨가 강화하는 **기술 타입**에 적용 | 사용자 선택한 게임 날씨 |
| 메가·원시 | 폼 능력치·타입·상황별 팀 보너스 및 추가 기술 | 체크 OFF/ON 분리 |
| 베스트 파트너 | 실제 현재 파트너로 활성화된 경우에만 해당 레벨 보정 | 단순 배지 보유와 활성 상태 구별 |
| 친구/파티 파워 | 초기에는 OFF; 추후 별도 시뮬레이션 토글 | 조건 누락 시 기본 미적용 |

참고할 알려진 기본값: 단일 약점 `1.6`, 이중 약점 `1.6 × 1.6 = 2.56`, 자속 `1.2`, 날씨 `1.2`, 그림자 공격 `1.2`. 구현 시 수치를 산재한 상수로 쓰지 않고 **버전 관리되는 규칙 테이블**로 취급한다. 실제 패치·특수 레이드/메가 신규 규칙에 따라 별도 계수나 적용 순서 검증이 필요하다.

### 24.4 기술 에너지·시간을 반영한 공격 주기

1. 노말 기술로 에너지가 쌓인다.
2. 현재 가진 스페셜 기술 1번 또는 2번을 사용할 수 있게 되면 선택된 정책에 따라 사용한다.
3. 스페셜 기술의 위력, 시전 시간, 에너지 소비량을 적용한다.
4. 일정 시간 구간의 누적 피해량/시간을 반복 계산한다.
5. 보스·날씨·폼 조건별 포켓몬 단위 DPS를 구해 순위를 산출한다.

**스페셜 기술 2개를 가진 포켓몬**은 두 기술을 모두 저장한다. 특정 보스에 대해 효과적인 기술을 골라 사용하는 공격 시퀀스를 비교한다. 다만 두 번째 기술을 실제로 해금하지 않았으면 가상의 기술을 추가하지 않는다.

```text
예: 같은 포켓몬의 현재 보유 기술
fast=A, charged_1=B, charged_2=C
  정책1: A + B를 최대한 활용
  정책2: A + C를 최대한 활용
  정책3: 에너지 상황에 따라 B/C를 혼합
→ 이론 모델에서 효율이 높은 실제 사용 가능 시퀀스를 선택
```

기술 자체의 `power / duration`만으로 순위를 정하지 않는다. 타입, 에너지 획득과 소모, 공격 모션 및 후속 행동 가능 시점이 반영되어야 한다.

### 24.5 CP·레벨·IV의 오차 처리

- CP는 공격/방어/체력을 합성해 계산되며, **동일 CP**라도 공격 IV·레벨이 다를 수 있다.
- 레벨 게이지 이미지, CP, HP, IV, 폼, 종족값을 조합해 가능한 레벨 후보를 역산한다.
- 후보 레벨이 복수이면 임의로 한 값을 확정하지 않고 `level_candidates`와 `confidence`를 남긴다.
- 서로 다른 레벨 후보에 따라 추천 순위가 바뀔 수 있다면 **정확도 주의/재스캔 필요** 표시.
- `level`이 없다는 이유로 무조건 DPS를 계산하지 말고, 확정된 IV·CP 기반 역산 또는 불확실성 처리 규칙을 갖춘다.

### 24.6 보스 기술·피격 에너지·생존의 올바른 위치

우리는 **화력 추천**을 하는 앱이다. 방어력이 높은 포켓몬을 우선하는 '안정성 추천 모드'는 만들지 않는다. 다만 **실제로 넣을 수 있는 화력**을 정밀 추정하려면 적의 기술, 기절 시점, 피격으로 얻는 에너지, 재입장 시간 등은 계산에 영향을 줄 수 있다.

**MVP:** 이 요소들을 제외한 이론적 지속 DPS를 기본 결과로 제공한다.

**고급 후속:** 보스 기술을 사용자가 지정하거나 가능한 기술 조합을 표본으로 시뮬레이션하고, `이론 DPS`와 `실전 예상 DPS`를 구분한다. 시뮬레이터의 평균 카운터 결과를 순수 DPS로 오인하지 않는다.

### 24.7 메가진화 토글이 일으키는 계산 변화

| 상태 | 계산 후보 |
|---|---|
| OFF (기본) | 실제 보유한 원래 폼·현재 기술로만 계산 |
| ON | 원래 폼 외에 **현재 조건에서 사용할 수 있는** 메가·원시 폼 후보를 추가하고, 사용 제약을 고려해 파티 최적화 |

- `현재 메가진화 가능한 개체` 여부와 **이미 메가진화해본 적 있는 개체**는 동일하지 않다.
- 메가진화하는 폼(X/Y 등)에 따라 종족값·타입이 달라질 수 있다.
- 일부 메가 상태에서 별도 추가 기술 또는 메가레벨 관련 보정이 있을 수 있으므로 2026년 이후 기능은 공식 규칙/게임 내 화면을 최신 기준으로 확인한다. **일괄적으로 CP에 동일 배율을 곱하지 않는다.**
- 실제 소지 메가에너지·필요량·재사용 대기 상태가 누락되었다면 `활성 가능 여부 미확인`으로 구별하고, 자동으로 '지금 가능'이라고 단정하지 않는다.
- 동일 개체를 원래 폼과 메가 폼으로 중복 선택하지 않는다. 동시 활성 제한 및 현재 게임의 전투 제약을 적용한다.
- 한 파티에서 메가 후보를 무조건 최우선으로 고정하지 않고, **6마리의 화력 목표와 팀/폼 보정**을 고려한다.

### 24.8 레이드 추천 검증 기준

| 테스트 | 기대 동작 |
|---|---|
| 같은 종, 같은 CP, 다른 실제 기술 | 보스에 따라 DPS 차이가 남 |
| 같은 종/기술, 공격 IV·레벨만 다름 | 계산값·순위가 필요한 만큼 차이를 반영 |
| 그림자 vs 일반 | 실제 그림자 공격 보정을 적용 |
| 메가 OFF/ON | OFF 결과에 메가 후보가 포함되지 않음 |
| 날씨 변경 | 강화되는 기술 타입만 관련 이득 발생 |
| 스페셜 기술 2개 | 실제 가지고 있는 기술 중 효율 높은 사용 패턴 반영 |
| 레거시 기술 | 현재 기술 목록에 없더라도 보유 기술이면 그대로 사용 |
| 특수 폼/메가 X/Y | 정확한 타입·종족값 분리 |
| 보스 이중 타입 | 두 방어 타입에 대한 상성 곱 계산 |
| 외부 참조 시뮬레이션 | 서로 같은 조건에서 오차와 순위 차이를 기록 |

## 25. 플레이어 관점의 필수·선택 고려사항 (v1.1 신규)

### 25.1 사용자에게 입력을 요구할 것은 최소한으로

**일반 레이드 추천의 기본 입력은 세 가지**다.

1. 레이드 보스와 정확한 폼 선택.
2. `메가진화 포함` 체크박스(기본 OFF).
3. **레이드 발생 지역의 게임 내 날씨** 선택(기본 `보정 없음`).

추가 조건인 보스의 현재 기술·친구 보너스·파티 파워는 기본 UI에 노출하지 않는다. 고급 설정이나 후속 개발로 둔다. 날씨 정보 자동 동기화는 사용자가 현재 플레이하는 장소/원격 레이드 위치와 어긋날 수 있으므로 사용자가 게임 내 날씨를 확인해 설정하는 설계를 우선한다.

### 25.2 상세 플레이어 체크리스트

| 확인 항목 | 플레이어 관점의 이유 | 앱의 처리 | 초기 범위 |
|---|---|---|---|
| 노말 기술 1개 + 스페셜 기술 1~2개 | 같은 포켓몬도 실제 기술에 따라 화력이 크게 변함 | 둘 다 수집, 가능한 조합 계산 | 필수 |
| 메가 X/Y·원시회귀 | CP·타입·기술·폼별 능력치 달라짐 | 기본 OFF, 체크 시 가용 후보 포함 | 필수 |
| 그림자/정화 | 같은 종이라도 피해량이 다름 | 개체 속성으로 저장 | 필수 |
| 날씨 | 레이드 기술에 위력 보너스 | 게임 내 날씨 직접 선택 | 필수 |
| 보스 폼 | 보스 타입·능력치가 달라질 수 있음 | 종과 폼 별도 저장 | 필수 |
| 보스의 실제 기술 | 실전 화력·에너지/기절에 영향 | 고급 모드에서 선택 가능 | 후속 |
| 베스트 파트너 활성 상태 | 현재 파트너일 때만 보정 | 보유 배지와 현재 활성 분리 | 조건부 |
| 친구 보너스 | 함께 참여할 때 피해량 달라짐 | 기본 OFF, 필요 시 추가 | 후속 |
| 파티 파워 | 파티 플레이 조건·스페셜 기술 강화 | 기본 OFF, 추후 옵션 | 후속 |
| 다른 트레이너의 메가 | 로비 전체 보정이 바뀔 수 있음 | 솔로 관점 가정 표시 | 후속 |
| 레이드 특수 메커니즘/방어막 | 일반 레이드 계산이 그대로 안 통함 | 특수 모드 경고/별도 엔진 | 후속 |
| 다이맥스·거다이맥스 | 3마리 파티, 다른 기술·역할 | 보유 여부 수집, 추천 엔진 분리 | 수집만 필수 |
| 재스캔 필요 여부 | 포켓몬 강화/기술 변경 후 저장값이 오래됨 | 마지막 확인 시간/수정 알림 | 필수 |

### 25.3 유용하지만 초기 프로젝트 범위에서 제외하는 기능

- '이 기술을 바꾸면 더 강하다', '사탕을 투자해 몇 레벨까지 강화하라' 같은 **미래 육성 시뮬레이션**.
- 친구 보너스·파티 파워·타인 메가를 포함한 모든 로비 환경의 실시간 자동 판별.
- 팀 전체 기절/회복 아이템 소비 최소화 같은 **생존 최적화**.
- 레이드 관련 공략 텍스트를 AI가 근거 없이 추측해서 만들어 내는 기능.

### 25.4 실제로 매일 쓰게 만드는 소규모 편의 기능

**A. 포켓몬 GO 검색 문자열 생성**

- 추천 포켓몬의 CP, 이름, 보유 기술, 앱에 저장된 별명 등으로 게임 속에서 해당 개체를 빨리 찾게 한다.
- Pokémon GO가 실제로 지원하는 검색어 문법만 사용한다. 개체별 완전한 식별자 검색이 불가능하면 검색 결과에서 수동 확인하도록 안내한다.
- 추천 결과에 **복사 버튼**을 제공하고, 검색 문자열이 완전한 6마리 고정 매칭을 보장한다고 주장하지 않는다.

**B. 마지막 스캔 시각/신뢰도 표시**

- 보유 포켓몬 카드마다 `마지막 검증 날짜`, `기술 확인 날짜`, `CP/IV 확인 날짜`, `OCR 상태`를 저장한다.
- 강화·진화·기술 변경·메가 상태 변화 등 수시로 바뀌는 정보는 오래된 상태임을 알리되, 정해진 기간만으로 강제 무효화하지 않는다.

**C. 필요한 개체만 증분 스캔**

- 최초에는 많은 포켓몬을 등록하더라도 이후 신규/변경된 포켓몬만 다시 업로드한다.
- 이름·CP·IV·별명 등이 같은 여러 개체를 단일 개체로 추정 합치지 않는다.
- 동영상 내 프레임/시간 정보를 근거로 '같은 개체 후보'를 제안하고 사용자 승인을 받는다.

**D. 샘플 검증 및 오류 수정 UX**

- OCR 원문과 해석된 기술명을 같이 표시한다.
- `확신 낮음`이면 원본 프레임을 볼 수 있게 해 빠르게 수정한다.
- 기술명이나 폼 변환에 실패하면 가짜 기술을 생성하지 않고 **미확인**으로 남긴다.

## 26. 데이터 모델 및 버전 관리 보강 (v1.1 신규)

### 26.1 외부 기준 데이터는 정규화해서 로컬에 저장

| 데이터 영역 | 제안 테이블 | 핵심 키/필드 |
|---|---|---|
| 내 실제 개체 | `owned_pokemon` | `uuid`, `species_form_id`, CP, IV, 레벨 후보, 그림자, 최근 스캔 시각 |
| 내 실제 기술 | `owned_pokemon_moves` | `pokemon_uuid`, `slot`(FAST/CHARGED1/CHARGED2), `move_id` |
| 포켓몬 종·폼 | `pokemon_species_forms` | `species_form_id`, `species_id`, 폼, 타입, 기초 공격/방어/체력 |
| PvE 기술 | `pve_moves` | `move_id`, 기술 타입, power, duration_ms, energy_delta, data_version |
| 포켓몬이 배울 수 있는 기술 | `species_move_pools` | `species_form_id`, `move_id`, 습득 구분/버전 |
| 타입 상성 | `type_effectiveness` | 공격 타입, 방어 타입, 배율, data_version |
| 날씨 룰 | `weather_boost_rules` | 날씨 코드, 강화 타입, multiplier, data_version |
| 포켓몬 레벨 상수 | `cp_multipliers` | 레벨, CPM, data_version |
| 메가 사용 상태 | `owned_mega_states` | `pokemon_uuid`, 메가레벨/경험/재사용/가용성 |
| 공유 자원 | `player_resources` | 진화 계열 ID, 사탕·XL·메가에너지와 업데이트 시각 |
| 레이드 보스 | `raid_bosses` | 보스 폼, 타입, 난이도/규칙, 확인일 |
| 원본 출처·해시 | `game_data_versions` | 소스 이름, URL, sha256, fetched_at, source_timestamp, 검증 상태 |
| 수집 이력 | `scan_sessions`, `scan_frames`, `observations` | 영상, 프레임 시각, 추출 원문, 모델 신뢰도 |
| 추천 실행 기록 | `raid_recommendations` | 요청 조건 + 데이터 스냅샷 버전 + 결과 |

### 26.2 내부 데이터 모델 사용 원칙

1. 포켓몬 종별 **종족값과 폼**은 외부 기준 데이터에 1회 저장하고, 개체별 CP/IV/기술은 따로 저장한다.
2. 사탕/XL사탕/메가에너지는 단순히 '포켓몬 한 마리의 고유 소유물'처럼 중복 저장하지 않고 적절한 공유/계열 단위로 관리한다.
3. `move_id`와 `species_form_id`를 내부 식별자로 사용하고, OCR에서 추출한 한글 명칭은 명칭 사전으로 변환한다.
4. 같은 포켓몬이 기술을 변경해도 이전 스캔값을 덮어쓰기 전에 변경 이력을 남긴다.
5. **레거시 기술** 등 최신 습득 가능 기술표에서 빠진 보유 기술을 유효한 현재 보유 상태로 보존한다.
6. 자료 출처가 충돌하면 그 사실을 남기고, 근거 없이 둘을 섞어 계산하지 않는다.

### 26.3 게임 데이터 업데이트 파이프라인

```text
[사용자 수동 업데이트 버튼 또는 정기 확인]
      ↓
[PoGo API api_hashes.json 해시 요청]
      ↓
[저장된 해시와 비교]
      ↓
[바뀐 파일만 다운로드]
      ↓
[JSON 스키마·타입·단위·ID 검증]
      ↓
[기존 규칙과 차이(diff) 생성]
      ↓
[임시 스냅샷에 적재]
      ↓
[회귀 테스트 / 샘플 포켓몬 DPS 검증]
      ↓
[정상 시 활성 버전 전환]
      ↓
[필요한 추천 결과만 무효화·재계산]
```

- 시간/에너지 단위 등 변환을 단위 테스트로 보증한다.
- 소스가 업데이트되었지만 파서가 실패하면 **이전 정상 버전 유지** + 경고를 표시한다.
- 출처별 갱신 시각을 별도 관리한다. '오늘 다운로드했음'과 '데이터 자체가 오늘 게임 최신 상태임'은 다르다.
- 외부 데이터를 갱신하더라도 `owned_pokemon`에 저장된 **실제 관측 정보**는 변경하지 않는다.
- 주기적 자동 갱신 기능은 별도 클라우드 운영 없이 사용자가 앱을 열었을 때 확인하는 방식으로도 충분하다.

### 26.4 추천 실행 결과의 재현성

다음 항목을 추천 결과에 함께 저장한다.

```json
{
  "boss": {"species_id": 150, "form": "NORMAL", "raid_tier": "UNKNOWN"},
  "weather": "NONE",
  "include_mega": false,
  "game_data_snapshot": "pogoapi-sha256-example",
  "owned_box_snapshot": "scan-session-example",
  "score_type": "cycle_dps_v1",
  "excluded_factors": ["boss_moves", "party_power", "friend_bonus", "dodging"],
  "results": []
}
```

위 JSON은 **API 계약 구조 예시**로서 레이드 등급·데이터 버전과 결과가 실제로 조회되었다는 뜻이 아니다.

- **1차 기능은 데이터 수집**, **2차 기능은 현재 보유 상태의 일반 레이드 최대 화력 6마리 추천**이다.
- 메가진화 **기본 OFF**, 필요할 때 체크박스로 켠다.
- 레이드 날씨는 사용자가 **게임에 표시되는 날씨**를 선택한다.
- 기술 변경 후/강화 후/진화 후의 예상 화력과 육성 계획은 제공하지 않는다.
- 맥스배틀용 추천 계산은 일반 레이드와 별도 후속 프로젝트로 둔다.
